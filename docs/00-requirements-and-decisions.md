# 00. 需求、术语与决策

## 目标

在 DeepSeek Harness 中提供一个同时包含后端和 UI 的 Agent Team 插件。用户可以维护助手模板，按具体任务组建团队，让不同模型驱动的独立 Agent 在共享 Workspace 中并行协作，并在工作完成后永久解散团队。

审核状态：当前 Harness 公开插件 API 可以完成团队解散的产品语义：停止成员、解除 Workspace 关联并永久删除团队领域记录。Harness 暂无 Session delete seam，因此旧 Session 物理日志保留在底层存储，但不再归属或恢复为团队成员。

## 语言与命名

- 设置页中文名称为“Agent 团队”，英文名称为“Agent Team”。
- 插件跟随 Harness 的 `zh/en` Locale 实时切换，不增加独立语言设置。
- 完整 UI 文案纳入同一 Locale namespace，不只翻译导航标签。

## 术语

| 名称 | 定义 |
| --- | --- |
| 助手模板（Assistant Template） | 可复用配置，包含名称、提示词、Provider、模型、预设、技能、工具和权限；本身不运行。 |
| 成员实例（Member Slot） | 某个助手模板加入某个团队后产生的运行实例，有自己的 `slotId`、Session 和运行状态。 |
| 团队（Team） | 共享 Workspace、成员实例、任务板和信箱的协作边界。 |
| Leader | 团队内唯一的协调角色，仍然是与其他成员平级的独立 Agent，不拥有其生命周期。 |
| Team Runtime | 插件后端持有成员 Agent Handle、投递消息、恢复 Session 和处理故障的运行时。 |
| Workspace | 所有团队成员共同读取和修改的同一个工作目录。 |
| 任务板（Task Board） | 记录任务所有者、依赖、状态、结果和文件范围的结构化协作数据。 |
| 信箱（Mailbox） | Agent 之间异步发送指令、进展、结果和告警的结构化消息通道。 |

## 功能需求

### 助手库

- 创建、查看、编辑、复制和删除助手模板。
- Provider 与模型从 Harness 当前配置中选择，并且是可启动助手模板的必填项；凭据只由 Harness 管理。
- 可配置系统提示词、预设、技能、工具白名单和权限策略。
- 删除模板前，如果它仍被活动团队引用，必须阻止删除并展示引用团队。

### 组建与维护团队

- 用户手工选择名称、Workspace、Leader 和成员实例；Workspace 可从已有列表选择，也可在组建团队弹窗中通过 Harness 原生目录选择器添加并立即选中。
- 一个模板可以加入多个团队，也能在同一团队中创建多个实例。
- 创建团队时只有一个 Leader；没有 Leader 或存在多个 Leader 都属于非法状态。
- 可以在运行中新增成员、移除普通成员；单个成员可停止当前输出，团队可清空全部任务与上下文。
- 移除普通成员会停止其 Agent、解除 Workspace 活动关联，并把 Session 索引保留为团队历史。解散团队时删除这些团队索引；底层 Session 日志因 Harness 限制仍可能保留。
- 更换 Leader 使用原子操作：先指定继任成员，再变更角色；不得先删除现任 Leader。
- 成员加入时复制助手模板快照。后续编辑模板不会暗中改变运行成员，用户可以显式选择“同步配置并重启”。

### 协作执行

- 每个成员拥有独立 Harness Session 和独立消息上下文。
- Leader 可拆分任务、指派成员、查询进度和汇总结果。
- 普通成员可更新任务状态、向 Leader 或其他成员发消息。
- 消息投递是异步的，不要求发送方等待接收方完成。
- 默认用户消息发给 Leader；UI 可以直接打开成员 Session 对话。
- 不自动把全部对话广播给所有成员，避免上下文膨胀和信息泄漏。

### 解散团队

- 解散是不可撤销的永久删除，必须二次确认并输入团队名称。
- 删除边界仅限当前团队实例：团队记录、成员实例、任务、信箱、活动和 Session 归属索引。底层 Session 物理日志不在插件可删除边界内。
- 不删除任何助手模板；即使某个助手只被该团队使用，也必须保留在助手库中，之后仍可用于组建新团队。
- 不删除或回滚 Workspace 中的任何文件。
- 删除过程必须可重试；部分失败时保留删除墓碑并继续清理，不得恢复为可运行状态。
- 运行时释放或团队领域数据删除失败时进入 `delete_blocked`，用户可重试解散。

## 核心技术约束

### 绝不使用 Subagent

以下约束是验收级别的不变量：

- 不调用 `ctx.subagents`、`dsh-tool-subagent` 或以 Job 代替成员生命周期。
- 成员 Session 不设置 `meta.origin = "subagent"`。
- 成员之间不设置 `parentSession`、委派深度或父子级联取消关系。
- 所有成员均由插件根级 `TeamRuntime` 通过 `ctx.agents.create` 或 `ctx.agents.resume` 创建与恢复。
- Leader 只是领域角色，不能直接拥有或销毁其他成员的 Agent Handle。

### Workspace 一致性

- 团队创建后保存规范化绝对路径和 Workspace 标识。
- 所有成员创建与恢复时使用同一 Workspace 上下文。
- MVP 不为成员创建独立 Git Worktree。
- 使用任务级文件范围和建议性租约降低并发写冲突，但不承诺像操作系统锁一样强制阻断外部修改。

## 非功能需求

- 可恢复：应用重启后可恢复团队、任务、信箱和成员 Session。
- 可观察：UI 能展示成员状态、当前任务、最后活动、错误和待批准事项。
- 幂等：创建、投递、状态更新和解散操作支持幂等键。
- 并发安全：团队变更使用 `revision` 或等价乐观锁，拒绝陈旧写入。
- 安全：Agent 只能访问其团队、任务和收件人允许的数据；危险工具仍走 Harness 审批机制。
- 可迁移：持久化记录带应用级 Schema 版本；升级使用可恢复的记录迁移，不依赖当前 Storage Backend 尚未提供的 Domain 原地 migration。
- 平台范围：首版是 `dsh web` 的 Host + Browser 插件；Electron 和 LAN 暴露需要独立的 Transport/信任边界验证。

## 暂不包含

- 自动推荐或自动组建团队。
- 跨机器分布式 Agent 调度。
- Workspace 文件自动回滚。
- 多 Leader、层级组织或 Leader 的 Leader。
- 自动将所有成员上下文合并为一个共享长对话。
- 自建模型 Provider、密钥或计费系统。

## 待实现前确认项

只有一个产品行为仍可配置化确认：是否允许用户直接向普通成员发消息。当前方案按“允许，但默认入口是 Leader”设计；将其改为“只读成员会话”只需要修改团队策略和 UI 权限，不改变存储与运行时结构。

## 验收标准

- 技术设计、领域对象、API 和 UI 中统一使用以上术语。
- 任意代码路径都不能把团队成员映射成 Harness Subagent。
- 删除、成员快照、唯一 Leader 和共享 Workspace 的行为均有自动化测试覆盖。
